# Product v0.4｜M3 真实浏览器验收服务规划报告

> 报告日期：2026-10-23
>
> 文档状态：规划基线，待团队确认后执行
>
> 仓库基线：`phase/product-v0.4@845eef8`（PR #19 已合并）
>
> 必要前置：PR #20（M1 第四步解锁修复）合入最新 Phase
>
> 目标：在功能冻结收尾前，交付一套可由产品负责人亲自操作并签字确认的真实浏览器验收服务

## 1. 结论

M3 定义为“冻结前真实浏览器验收服务与人工 UAT 门禁”，不承担 M2、M5
或后端数据库功能的开发。M3 负责把各方已经完成的成果集成为一个可重复
启动、可追溯、可回滚的 Release Candidate（RC），完成技术预验收后交由产品
负责人在真实 Chrome 或 Edge 中操作，并以明确的人工结论决定是否可以冻结。

本报告默认采用本机验收服务：正式前端构建、真实 FastAPI、真实数据库和真实
LLM Provider 均在验收环境中运行，浏览器访问 `http://127.0.0.1:5174`。这不是
公网部署方案；如需跨设备或公网 URL，应另立部署任务并补充网络、域名、TLS、
访问控制和密钥管理要求。

## 2. 范围边界

### 2.1 M3 负责

- 建立最新 Phase 上的干净 M3 分支和独立工作树；
- 提供可重复的一键启动、健康检查、日志和统一关闭能力；
- 使用生产构建产物提供前端，而不是以 Vite 开发模式作为最终验收依据；
- 集成 M2、M5 和数据库交付物，并逐项执行集成回归；
- 运行 Python、前端构建、真实服务浏览器 E2E、真实 LLM smoke 和安全检查；
- 固定不可变 RC commit，提供人工验收入口和验收脚本；
- 记录人工验收结果、问题、截图、日志索引和最终冻结结论。

### 2.2 M3 不负责

- 开发或重写 M2；
- 开发或重写 M5；
- 设计数据库表、迁移和持久化业务逻辑；
- 替代外部负责人解决其分支内部功能缺陷；
- 引入新的公开 API、Schema 或 Core 状态规则；
- 公网部署、生产域名、TLS 或云资源建设；
- 在产品负责人验收前直接宣布功能冻结。

### 2.3 外部交付责任

M2、M5 和数据库由外部负责人实现。M3 只消费已经通过各自单元测试、附有
变更说明并可独立合入的 PR。若外部交付改变冻结 API 或 Schema，必须先走
Contract Change Proposal，不能在 M3 中静默兼容。

数据库交付至少应包含：

1. 环境变量和 Secret 约定；
2. 初始化及迁移命令；
3. 验收数据或测试账号初始化方式；
4. 数据重置方式；
5. 健康检查；
6. 刷新、重启、退出登录后的持久化预期；
7. 不在日志、前端构建或 Git 中泄漏凭据的证明。

## 3. 当前仓库审计结论

1. `phase/product-v0.4@845eef8` 已包含 PR #19 的产品闭环。
2. M1 修复位于 PR #20，尚未进入 Phase；M3 不得绕过该 PR 建立最终 RC。
3. 当前 Product CI 已包含 Python 回归、前端构建、真实 API/Web 启动和浏览器

   已覆盖配置解析、端口检查、健康等待、浏览器打开和进程清理，但它：
   - 基于旧提交 `605579e`；
   - 含未提交改动；
   - 只覆盖旧 DeepSeek 配置名，未完整匹配当前多 Provider 设置；
   - 启动 Vite 开发服务，而非生产构建；

6. 根工作树落后远端且存在大量用户改动，不得作为 M3 开发或验收基线。

## 4. M3 任务分解

### M3.0｜基线与服务契约

前置：PR #20 已合入 `phase/product-v0.4`。

- 从最新 `origin/phase/product-v0.4` 创建
  `task/product-v0.4-m3-acceptance-service`；
- 固定 API `127.0.0.1:8001` 和 Web `127.0.0.1:5174`；
- 定义 `preflight → build → start → ready → open → stop` 生命周期；
- 定义日志目录、脱敏规则、健康检查和退出码；
- 定义验收模式对干净工作树、RC commit、数据库迁移和 LLM 配置的要求；
- 明确普通本地开发模式与正式验收模式的差异。

退出标准：服务契约、配置清单和错误码可以在不阅读实现的情况下被另一名开发者
执行和审查。

### M3.1｜一键启动与正式构建服务

- 从旧启动器草稿选择性移植安全的配置解析和进程生命周期逻辑，不整分支合并；
- Windows 提供仓库根目录双击入口，同时保留可脚本化的 CLI；
- 验收模式先执行前端生产构建，再以固定端口提供构建产物；
- 为 Preview 增加与开发服务一致的 `/api` 和 `/healthz` 代理，或采用等价的单源
  静态服务方案；
- 启动 FastAPI、数据库依赖和前端服务，逐项等待 readiness；
- 默认拒绝复用未知或旧版本端口进程，防止验收错误 commit；
- 输出版本、Git SHA、服务地址和运行模式，但不输出任何 Secret；
- 浏览器自动打开失败时仍打印可复制 URL；
- Ctrl+C 或启动失败后只清理本轮创建的进程；
- 日志写入 Git 忽略目录，并具备 API Key、密码和连接串脱敏规则。

退出标准：在干净环境完成“一次命令启动—浏览器打开—正常关闭—再次启动”，
且不会残留端口或泄漏密钥。

### M3.2｜自动化技术预验收

必须覆盖：

- Python 全量回归；
- 前端 TypeScript 检查和生产构建；
- 正式构建模式下的真实 API + Web 浏览器 E2E；
- 1280×720、768×1024、390×844 三视口；
- M1 回归：先收集 E01/E02/E03，再提交初始和修正假设，诊断能够解锁；
- 正确、部分正确、错误、证据不足和重复提交；
- 登录与未登录边界（外部功能合入后）；
- 数据库迁移、写入、读取、刷新和服务重启恢复（外部功能合入后）；
- 真实 LLM Provider 成功调用一次；
- Provider 超时、畸形输出、敏感信息泄漏时安全回退；
- 前端构建、HTTP 响应、Trace 和日志中不存在密钥及隐藏 Case 字段；
- 启动失败、端口冲突、数据库不可用和前端构建失败均给出可操作错误。

退出标准：自动化门禁全绿，真实 LLM smoke 只记录 Provider、模型、时间和结果，
不记录 Key、完整 Prompt 或私有 Case 内容。

### M3.3｜外部成果顺序集成

推荐顺序：

```text
PR #20 / M1
  → M2
  → 数据库与迁移
  → M5
  → M3 验收服务适配
  → 全量集成回归
  → 固定 RC
```

每项合入前后都记录测试差异。禁止把 M2、M5 和数据库三个大分支一次性合并后
再统一排错。若某项未达到自身交付标准，应退回责任人修复，而不是在 M3 分支
复制实现形成第二套逻辑。

退出标准：最新 Phase 包含所有计划能力，工作树干净，CI 全绿，并生成唯一 RC
commit。RC 确定后，在人工验收完成前禁止合入非阻断性改动。

### M3.4｜产品负责人真实浏览器验收

由产品负责人使用真实 Chrome 或 Edge，在 M3 提供的服务上完成。建议控制在
15 分钟内。

| 序号 | 操作 | 通过标准 |
|---|---|---|
| 1 | 使用全新浏览器会话打开验收 URL | 页面来自指定 RC，无控制台阻断错误 |
| 2 | 使用验收账号登录 | 登录成功；错误凭据提示明确且不泄漏信息 |
| 3 | 进入 ST-001 并播放、暂停、继续动画 | 动画状态清楚，学习 Trace 未被播放控制污染 |
| 4 | 先收集 E01、E02、E03 | 每条证据仅在请求后出现，未释放数据不提前暴露 |
| 5 | 提交初始假设 | 保留输入和历史，诊断仍未解锁 |
| 6 | 不再取证，直接提交修正假设 | 诊断立即解锁，第四步不再卡住 |
| 7 | 请求一次智能助教 | 页面明确显示真实 LLM 模式，响应不泄漏标准答案 |
| 8 | 提交诊断并查看报告 | 判定、引用证据、五维评分和 `not_assessed` 正确 |
| 9 | 刷新页面或重新登录 | 数据按数据库需求恢复，不发生会话串扰 |
| 10 | 检查桌面和手机宽度关键操作 | 主流程可达，无关键遮挡或横向溢出 |
| 11 | 关闭并重新启动服务 | 服务可重复启动，端口与数据状态符合约定 |

验收记录至少包含：

- RC commit；
- 日期、操作系统和浏览器版本；
- 配置摘要与 Provider/模型名称，不含密钥；
- 通过项、问题项、截图和日志索引；
- 产品负责人的明确结论：通过、整改后复验或不通过。

### M3.5｜冻结证据与收尾

- 输出自动化测试报告、人工验收记录和已知限制；
- 将所有阻断问题关联到 RC 和修复 PR；
- 若修复影响登录、持久化、学习流程、LLM 或报告，生成新 RC 并重验相关路径；
- 人工确认通过后，更新 Product v0.4 任务计划和发布门状态；
- 再按分支政策推进 `phase/product-v0.4 → develop`，不直接跳到 `main`；
- 冻结后只接受经批准的阻断性修复。

## 5. M3 门禁矩阵

| 门禁 | 责任 | 进入条件 | 退出条件 |
|---|---|---|---|
| G0 基线 | M3 | PR #20 已合入 | 干净 M3 分支建立 |
| G1 服务 | M3 | 服务契约确认 | 一键启动、正式构建、健康检查和关闭通过 |
| G2 外部交付 | M2/M5/数据库负责人 | 独立 PR 与测试就绪 | 分项合入且回归通过 |
| G3 技术预验收 | M3 | 所有计划能力已集成 | CI、E2E、安全检查、真实 LLM smoke 全绿 |
| G4 人工 UAT | 产品负责人 | 唯一 RC、服务和验收数据就绪 | 明确签字结论为通过 |
| G5 冻结 | 团队 | G4 通过且无阻断问题 | 证据归档并推进 Phase→Develop |

## 6. 完成定义

M3 只有同时满足以下条件才算完成：

- [ ] PR #20、M2、数据库、M5 均已进入最终集成基线；
- [ ] 一键启动使用正式前端构建和真实后端；
- [ ] 数据库迁移、健康检查、验收账号和重置流程可执行；
- [ ] 真实 LLM 成功 smoke 已完成；
- [ ] Python、构建、浏览器 E2E、三视口与安全门禁全部通过；
- [ ] RC commit 唯一、远端可追溯、工作树干净；
- [ ] 产品负责人完成真实浏览器主流程；
- [ ] 产品负责人给出明确的“通过”结论；
- [ ] 验收证据已归档且不包含任何 Secret；
- [ ] 验收后没有未经复验的功能改动；
- [ ] Phase→Develop 冻结前 PR 已具备进入条件。

## 7. 主要风险与控制

| 风险 | 影响 | 控制措施 |
|---|---|---|
| M2/M5/数据库延期 | M3 无法固定 RC | M3.0–M3.2 先并行完成，G3/G4 等待外部交付 |
| 旧启动器直接合并 | 配置漂移、遗漏 M1、错误运行模式 | 只选择性移植到最新 Phase，不整分支合并 |
| 验收使用 Vite dev | 不能代表生产构建 | 强制生产 build + Preview/等价静态服务 |
| 端口上已有旧服务 | 用户验收错误版本 | 验收模式默认拒绝复用，并打印 commit |
| 数据库缺少可重复数据 | 验收结果不可复现 | 外部负责人提供迁移、seed、账号和 reset |
| LLM 网络波动 | 真实调用不稳定 | 技术 smoke 先通过；人工验收保留安全回退证据 |
| 验收后继续改功能 | 签字与实际发布版本不一致 | 任何关键改动生成新 RC 并复验 |
| 日志或构建泄漏密钥 | 安全阻断 | 后端注入、前端环境隔离、日志脱敏和 Secret 扫描 |
