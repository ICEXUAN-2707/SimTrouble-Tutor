## 目标与范围

使用 SQLite 保存账号所属的已完成训练记录和权威报告。API 重启、退出后重新登录时，
持有训练 Session ID 的原用户仍可读取已完成报告；其他用户及匿名请求不能访问。
保持现有五维评分、报告 JSON 和 create-once 语义。

本轮不要求恢复未完成会话或 Tutor 对话，不引入新数据库服务、队列或事件溯源。
不持久化密码明文、认证/CSRF Token、Provider 凭据、完整 Prompt 或 Provider 错误响应。

## 内部存储接口

| 操作 | 输入 | 返回及保证 |
| --- | --- | --- |
| `save_completed` | 账号 ID、已评估的公开 SessionView、TrainingReportV04 | 单事务写入；Session ID 唯一；相同记录重试可幂等，冲突报告拒绝覆盖 |
| `get_completed` | 账号 ID、Session ID | 所属用户的已完成快照；缺失及非所属用户统一返回不可见 |
| `list_completed` | 账号 ID、有界分页参数 | 内部查询已完成记录的摘要；不得把其他用户记录加入结果 |

Application 层负责所有权校验和存储事务，Core 不依赖 SQLite 或身份库。
前端及 Tutor 不能直接写存储。权威报告生成后再存储，不从历史 LLM 文本重算分数。

## 数据与迁移

在现有本地 SQLite 存储基础上新增版本化迁移，保留账号、认证会话和登录限制数据。
不单独修改 `PRAGMA user_version` 而绕开现有迁移入口。
实现前确定训练表与身份表使用同一数据库及迁移管理器，或显式使用独立数据库和独立版本号；
不得让两个初始化器对同一版本号作不同解释。

每条记录至少含：存储格式版本、Session ID、所属账号 ID、Case ID、完成时间、
现有公开 SessionView JSON、现有 TrainingReportV04 JSON。
Session ID 建唯一约束，账号 ID 与完成时间建查询索引。
读取时通过现有 Pydantic 模型校验版本和 JSON，不能把损坏记录当成空报告或生成伪造评分。

写入报告及完成快照必须在一个事务内。需要故障注入测试确定：SQLite 写入失败时，
API 不能宣称记录已持久化，也不能留下“内存已提交、数据库未写入且无法重试”的状态。
诊断持久化与现有会话锁、评估仓库 create-once 逻辑必须一起审查。

## 公开接口边界

优先复用 `/api/v0.5/sessions/{session_id}` 和已有 Report GET 路由读取持久化结果，
保留认证、CSRF、所有权和统一不可见错误语义。
匿名 v0.4 路由不能读取账号所属的历史记录。

前端历史记录列表若需要新的公开路由或响应模型，先提出并审核 Contract Change Proposal，
再更新冻结契约；本草案没有授权增加公开接口。
旧 v0.5 文档中的“训练记录仅内存”说明在实现并通过测试后统一更新。

## 验收

1. 用户 A 完成训练，关闭应用，使用同一数据库创建全新 API 实例；A 登录后能读取同一报告。
2. 用户 B 和匿名 v0.4 请求无法读取 A 的已完成 Session 或报告，错误不泄漏归属信息。
3. 相同报告重复持久化不生成重复记录，冲突报告不能覆盖原报告。
4. 写入失败、损坏 JSON、更新版本数据库、旧版本迁移均有明确可验证行为。
5. 原账号、密码校验、认证会话与登录限制数据在迁移后保持有效。
6. ST-001 Safety 仍为 `not_assessed`；同一记录重启前后报告内容及评分一致。
7. 后端全量回归、生产构建、登录与报告浏览器流程通过。
8. 若新增公开历史列表，先通过契约变更评审，再验证分页和跨用户隔离。
